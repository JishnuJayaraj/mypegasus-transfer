# ADR-0007: Authentication and authorisation

- Status: Accepted (provisional: Q7, Q11, Q27, Q28 are still `assumed`)
- Date: 2026-10-15 (amended the same day from the decisions log)

## Decision
- **Staff:** Microsoft Entra ID via a plain OIDC client (no adapter). MFA is enforced at the IdP
  (Conditional Access). Roles and project assignments are managed **in the app**, not taken
  from Entra groups. Server-side sessions in httpOnly, SameSite cookies, 8 hours, with CSRF
  protection. Dev/test: a stub login with a user switcher.
- **Participants:**
  - The mobile number is the primary channel (SMS magic link or one-time code). Private email
    is secondary. **Imported work emails are never used.**
  - Single-use, 15 minutes, at most 5 requests per hour per phone/email.
  - Sessions: 30 minutes idle, 12 hours absolute.
  - Date of birth as a knowledge check before special-category data is shown.
  - Fallbacks: printable one-time access code, and assisted mode.
- **Assisted mode:** staff act on behalf of a participant (`actor` + `onBehalfOf` in the audit),
  without sharing a session.
- **Authorisation:** role × project × assignment, checked in the API for every request, never
  only in the UI. Roles: Admin, Regional admin (region = Niederlassung), PL, Berater/Profiler,
  Back office, Participant. **No customer role in the MVP** (Q47). The field-level access
  matrix is in `docs/domain/data-protection.md`. Special-category data is served by separate
  endpoints with read logging. Break-glass requires a reason and is flagged for review.

## Consequences
- About 5–10 % of participants need assisted mode or printed codes (Q11).
- Revoking consent for the private mobile/email leaves only assisted mode or a printed code;
  the UX must cover this.
- **The field-level access matrix is pure domain logic in `packages/domain`, built with tests in
  Slice 1** (accepted in the PR #1 review). Slice 3 only connects login and identity.
- Participants log in to `apps/portal`, staff to `apps/web` (ADR-0001), with separate session
  cookies.

## Amendment 2026-10-20: personal activation codes ([round 35](../decisions/2026-10-20-answers-round-35.md))

- **First access** is a personal, single-use activation code per participation, generated when it
  is issued, never at import. The PL chooses the channel per participant: a printed letter to the
  imported address, a sheet at the info event (both with a QR of the personal link, the code in
  the fragment), or in person, sent to a private email or mobile the person gives after an ID
  check; the person then activates on their own device and the PL never sees the code (Q120). Only a keyed hash is
  stored. It is valid 30 days from issuance and locked after 5 failed attempts; a new issuance
  revokes the old code. Only the PL or assigned back office issue or reissue, after verifying the
  person; there is no anonymous or self-service reissue; every issuance is audited (Q118). The
  letter or sheet is also the Art. 14 GDPR notice (Q114).
- **Activation** binds the account to the imported participation. The steps are the knowledge
  check (date of birth; without one, no self-activation: the PL hands the code over after an ID
  check, Q113), at least one private email or mobile chosen by the participant with consent
  (Q117, Q119), and confirmation by a one-time code. A notice then goes to that channel.
  Activation moves `imported` or `unreachable` to `contacted` in the same transaction (Q116).
- **Login** afterwards is a one-time code (or a link that takes effect only on a click on the
  page) to the registered channel, with the 15-minute and 5-per-hour limits above. Mobile is no
  longer the primary channel by default.
- **No self-registration** and no project QR: Slice 4c is dropped and `self_registered` leaves
  the lifecycle.

## Amendment 2026-10-20: plan review ([round 36](../decisions/2026-10-20-answers-round-36.md))

- A sheet is activatable only after its audited handover following a photo-ID check; a letter's
  assurance is the code plus the birth date (Q127, Q129). The Art. 14 notice goes out at issuance
  (Q124). Staff never see a participant's registered address (Q123). Lost access is a recovery code
  that suspends the old channels at once (Q130). Details: data-protection.md, Authentication.
- Activation codes, delivery addresses and one-time codes are keyed with HKDF from a separate
  `ACCESS_CODE_SECRET`; rotating it voids open codes, never sessions.
- Messages carrying a secret are sent after the code or challenge is committed, never inside a
  transaction; the outcome is recorded afterwards. Notices without a secret are sent at least once
  by a job.
- Only a global admin manages staff accounts and org roles; org roles are region-scoped (Q126).
- Design and PRs: [Slice 3 plan](../plans/archive/slice-3.md) (archived).

## As built 2026-10-20: staff sessions and OIDC login (Slice 3, PR 3b)

- **One session store for both modes:** `staff_session` (token SHA-256 as the key, staff user,
  `created_at`, `expires_at` = start + 8 hours, `ended_at`, `end_reason` `logout`, `superseded` or,
  from 3c, `deactivated`). Written only by `start_staff_session` and `end_staff_session`; the API
  reads it and checks expiry against database time (`apps/api/src/session.ts`). The Slice 0 signed
  cookie is gone. `GET /api/v1/me` returns `sessionExpiresAt`.
- **Cookie:** `__Host-tp_staff` (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`) outside
  development, `tp_staff` over http in development; 32 random bytes, base64url. Staff routes read
  only this cookie. A 401 leaves a dead cookie in place: clearing it could delete a newer login's
  cookie when a request with the superseded token is still in flight.
- **OIDC (`AUTH_MODE=oidc`):** `openid-client` 6 (pinned), authorization code flow with PKCE
  (S256), `state` and `nonce`, `client_secret_post`. Discovery runs at the first login and is
  cached; a failure is retried at the next. `GET /api/v1/auth/login?returnTo=` redirects to the
  identity provider and sets `tp_oidc`: `state`, `nonce`, the verifier and the return path, signed
  with HMAC-SHA256 under an HKDF key from `SESSION_SECRET` (`oidc-flow-cookie:v1`), expiring after
  10 minutes inside the signed value, `HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth`.
  `GET /api/v1/auth/callback` clears it, redeems the code at the redirect URL as configured (never
  the request's `Host`) and redirects to the return path, or to `/login?error=<code>`:
  `unknown_account`, `account_deactivated`, `identity_mismatch`, or `login_failed` for any failed
  check. The return path is `/` or a path below `/projects` or (from 3c) `/admin`
  (`safeReturnPath`); anything else returns to `/`. `POST /api/v1/auth/logout` ends the session in both modes; it doesn't end the
  identity provider's session.
- **Binding and refusals:** `staffLoginDecision` (domain) decides; `bind_staff_identity`,
  `start_staff_session` and `record_staff_login_refused` write, with their `staff_audit_event`
  (data-protection.md, Authentication).
- **Start-up:** `AUTH_MODE=oidc` refuses to start without `OIDC_ISSUER`, `OIDC_CLIENT_ID`,
  `OIDC_CLIENT_SECRET` and `OIDC_REDIRECT_URL`; outside development both URLs must be https, and
  the redirect URL must be `/api/v1/auth/callback` on an origin in `APP_ORIGINS`. `AUTH_MODE=dev`
  stays refused in production.
- **Dev stub:** `POST /api/v1/dev/session` starts a session in the same store (method `dev`), so
  nothing differs after login; a deactivated account is a 422 `account_deactivated`.
- **Web:** `/login` shows "Anmelden" (to `/api/v1/auth/login`) in OIDC mode and the user switcher
  in dev mode; the header shows the user's name and "Abmelden"; a 401 after a session returns to
  `/login` with "Sitzung abgelaufen" and the page asked for.
- **Tests:** OIDC runs against a local test issuer in the test suite (discovery, JWKS and the token
  endpoint, signed with `jose`; `apps/api/src/oidc-test-issuer.ts`), never a real identity
  provider.

## As built 2026-10-20: org model, teams and assignments (Slice 3, PR 3c)

- **No flat staff role** (Q126). A staff user has `mayCreateProjects`, zero or more org roles
  (`staff_org_role`: `admin` global, `regional_admin` and `regional_operations_manager` per
  region) and zero or more project roles (`project_membership`). The session carries the flag and
  the org roles (`GET /me`); the project roles and the open participant assignments are loaded per
  request (`apps/api/src/access.ts`, `staffSubjectOf`), so a change takes effect at the next
  request, an ended assignment too.
- **Regions:** `PermissionTarget.regionId` is the project's region. A regional role sees and acts
  only on projects of its regions; a project without a region (only those created before) is seen
  by global roles and its members (`seesProject`). The creator chooses the region of a new project;
  its PL changes it while draft, a global admin at any time (`regionChangeRefusal`).
- **Administration** (`/admin/staff`, `/admin/regions`): only a global admin creates, changes and
  deactivates accounts, grants org roles, sets `mayCreateProjects` and maintains regions; never
  their own deactivation or admin role. Authority-removing operations serialise on one transaction
  lock and re-check the actor, so concurrent mutual operations preserve an active admin (Q131).
  Deactivation removes the account's org roles and memberships, ends its sessions and assignments
  in one transaction, and is refused for a project's last active PL; role removals remain audited.
- **Teams and assignments:** the PL adds and removes members and roles (the project's "Team" tab,
  with a name search over active staff, `GET /staff-directory`) and assigns participations to the
  project's consultants (Q62); a global admin may add a replacement PL, never themselves, and
  gains no case access by it. Regional admins manage no team. Removing `consultant` ends that
  person's assignments in the project.
- **Dev switcher:** "Name · Rolle" shows the role a user is best known by (`staffRoleLabel`: an org
  role, else PL for the project-creation flag or a PL membership, consultant, back office).

## As built 2026-10-21: activation-code issuance (Slice 3, PR 3d)

- A project lead or back-office member of the project may issue, hand over and revoke activation
  codes and provide Article 14 notices. Consultants, org administrators, participants and
  anonymous callers cannot. The API checks visibility and operation permission for every request;
  action routes also bind the code id to the participation id in the path.
- Codes are twelve uniform Crockford base32 symbols generated from independent random bytes and
  shown grouped as `XXXX-XXXX-XXXX`. The database receives only an HMAC-SHA-256. Separate keys are
  HKDF-derived from `ACCESS_CODE_SECRET` using `activation-code:v1`, `delivery-address:v1` and
  `one-time-code:v1`; no activation key is derived from the staff-session secret.
- Printable codes exist only in the no-store issuance response and the staff print view. QR links
  put the ungrouped code in the URL fragment, which is not sent to the server. In-person responses
  contain neither code nor destination; the database keeps only the destination's keyed hash.
  Codes, destinations and hashes are absent from audit details, application logs and later API
  responses.
- Letter issuance requires the imported address and birth date. Sheets remain `printed` until an
  audited photo-ID handover. In-person issuance records the photo-ID check, commits a pending code,
  then sends outside the transaction. A reissue requires `replaceOpenCode: true` and atomically
  revokes the previous open code. Terminal status changes revoke open codes in their own status
  transaction.

## As built 2026-10-21: portal activation and participant sessions (Slice 3, PR 3e)

- **Sessions:** `participant_session` like the staff store: the cookie `__Host-tp_portal`
  (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`; `tp_portal` over http in development) carries
  32 random bytes, the row their SHA-256. 30 minutes idle and 12 hours absolute by database time;
  the API moves `last_seen_at` at most once a minute. A submitted code starts an `activating`
  session, which opens only the activation steps; completion ends it (`activated`) and starts an
  `active` one with a new token. A terminal status ends every session of the participation.
  Portal routes read only the portal cookie; staff routes only the staff cookie.
- **Steps (D23):** the code (from the link's fragment, removed from the address bar, posted only
  on a click) → the Art. 14 notice repeated (the version shown is recorded on
  `participant_activated`) → the birth date (skipped only for a handed-over sheet or an in-person
  code without one, Q129) → for an in-person code the retyped delivery address (its keyed hash
  against the code's), else a private email or mobile with the `portal-contact-consent:v1` consent
  and a six-digit one-time code to it → completion. `packages/domain/src/activation/steps.ts`
  holds the machine; the functions repeat it under their locks.
- **Identity assurance (D29):** the account records `birth_date`, or `photo_id` with the code's ID
  check (confirmer, time) when the birth-date step was skipped; the session records the step-up
  (`birth_date`, else `one_time_code`) with its time.
- **Limits:** `packages/domain/src/portal/limits.ts` (D14, D27, D29), held to the SQL by
  `packages/db/src/portal-limits.int.test.ts`. Every code submission (code, birth date, delivery
  address, completion) passes an in-memory per-IP throttle of 10 per 15 minutes; a shared limiter
  and the client IP behind the ingress are pre-pilot items (ADR-0005).
- Logout is `POST /api/v1/portal/logout` (audited for an active session). Login with a one-time
  code, channel management and lost-access recovery are PR 3f (below).

## As built 2026-10-21: portal login, channels and lost-access recovery (Slice 3, PR 3f)

- **Login (D27):** `POST /api/v1/portal/login/code-request` with the kind and address answers
  `202` with no body whether or not the address is a live channel (not removed, not suspended) of
  a usable account (active project, participation not terminal); only then is a `login`
  challenge committed (`request_login_code`). The send runs after the response (`detached.ts`; the
  code lives only in that closure, never in a job payload), so a known address isn't slower; its
  outcome is recorded by `record_login_code_delivery` (a failure invalidates the code unless a
  newer one superseded it). The email carries the code and `<PORTAL_PUBLIC_URL>login#<code>`; the
  page moves the code into its field, removes it from the address bar and logs in only when the
  participant types the address and clicks "Anmelden". The link carries no address.
  `POST /api/v1/portal/login` (`start_participant_session`) checks the code sent to that very
  address and starts an `active` session with the step-up `one_time_code`, audited
  `participant_login`. An unknown address, a wrong, expired or used code and the fifth wrong entry
  all get the one answer `one_time_code_invalid`.
- **Rate limits:** login codes are counted per address and hour in memory for every address alike
  (keyed hashes under the delivery-address key), so the sixth request is a `429` whether or not the
  address has an account. The database's own limit (5 per address and hour, login and
  verification codes together) still applies to known addresses; when it alone refuses a login
  code, the request is accepted and nothing is sent, because a `429` would tell the address apart.
  Login and verification submissions pass the per-IP throttle too.
- **Channels (D28):** `GET /portal/channels`; `POST /portal/channels` sends a verification code to
  a new private address (`request_channel_code`; a taken address, the participant's own included,
  is `channel_in_use`, the work email `channel_invalid`); `POST /portal/channels/verification`
  adds it with its own consent record (`add_participant_channel`); `DELETE /portal/channels/{id}`
  removes it and ends its consent `revoked` (`remove_participant_channel`). Removing the last
  channel ends every session of the participant (`no_channel`): without a channel there is no
  login until staff issue a recovery. The portal warns before that removal.
- **Recovery (D24, Q130):** `POST /api/v1/participations/{id}/activation-codes` with purpose
  `recovery`, by letter, sheet or in person, after the PL or back office confirm that they
  verified the person (`identityVerified`; an in-person code records the photo-ID check as at
  first issuance). Only for an activated account (`not_activated` otherwise); no cutoff (an
  activated account stays usable until the participation is terminal, Q121). Issuing it ends all
  the participant's sessions (`lost_access`) and suspends every live channel in the same
  transaction (`contact_channels_suspended`); a suspended channel neither logs in nor gets
  notices. The participant then runs the activation steps with the recovery code (the same birth
  date and channel rules); completion removes the old channels and ends their consents with
  `lost_access_replaced` (never a withdrawal), adds the new channel and consent, changes no status,
  keeps the account's first identity assurance and is audited as a `participant_login` naming the
  code. The participant's own old address may be registered again. If the code expires or is
  revoked, the old channels stay suspended and the PL issues another.

## Note 2026-10-15: Slice 0 dev stub (superseded by Slice 3, PR 3b)

Slice 0 implements only the dev stub (`AUTH_MODE=dev`, plan section 5.4): a signed httpOnly
cookie `tp_staff_session` (`SameSite=Lax`) with a staff user id and the issue time, set by the
dev-only `POST /api/v1/dev/session`. It is **not** the session model above: there is no
server-side session store, no lifetime and no role checks yet. The server-side store, the
8-hour lifetime, OIDC and the participant cookie come in Slice 3. The API refuses to start with
`NODE_ENV=production` and `AUTH_MODE=dev`, and `AUTH_MODE=oidc` fails at startup until Slice 3.
