# Database: function and trigger sources

## Function and trigger sources

The current rule (Slice 7b, D1; Q256). The amendments below name the migration that first held a
function: that is history. **What a function does today is in its source file.**

- **One file per function and per table's triggers.** `packages/db/sql/functions/<area>/<name>.sql`
  holds the function (`CREATE OR REPLACE FUNCTION`, every overload), its owner and its grants
  (`REVOKE ALL … FROM PUBLIC`, then each `GRANT EXECUTE`); `packages/db/sql/triggers/<table>.sql`
  holds the table's triggers (`CREATE OR REPLACE TRIGGER`), except the evidence-only trigger,
  which one generated source holds for every table (generated lists, below). Names are
  schema-qualified, so a source doesn't depend on the session's `search_path`. `packages/db/sql/manifest.json` lists
  every source in the order it is applied; a file the manifest doesn't list, or a listed file that
  is missing, stops the run.
- **Changing a function is editing its file** (for a generated source, its template: generated
  lists, below). `pnpm db:migrate` runs the migrations and, after
  they have committed, applies every source whose SHA-256 differs from the one recorded in
  `function_source` (name, hash, time; no personal data, `reference_data`, owner only), in the
  manifest's order, **in one transaction or not at all**. A failed migration ends the run before
  any source, and the runner itself refuses a database that isn't at the journal's last
  migration. `db:reset`, the test databases, the e2e setup and the image (`dist/migrate.js` with
  `dist/sql`) all go through `runMigrations`, so there is one path. A second run applies nothing.
- **A new function** is a new file, listed in the manifest after the functions it calls (an SQL
  function's body is checked when it is created), with its owner and grants.
- **A migration is still needed, and only, for** tables, types, enum values, grants on tables and
  data, and for dropping a function, an old signature or a return type (`CREATE OR REPLACE` can't
  change those), together with removing or changing the source. Sources run after the migrations,
  so a function may use an enum value added in the same PR; a migration never calls a function
  whose source the same PR changes.
- **The allowlist** (`migrationOwnedFunctions` in the manifest): a function that a table's
  constraint, default or index expression depends on has no source and stays in migrations,
  because replacing it would not revalidate the rows or rebuild the index. It is empty today; a
  test fails when it differs from what the catalog's dependencies say.
- **Merged migrations are never edited** and stay the history. The first sources are
  `pg_get_functiondef` and `pg_get_triggerdef` of a database migrated to `0115`, bodies verbatim
  (`packages/db/sql/extraction-baseline.json` holds their hashes).
- **Tested** (`function-sources.int.test.ts`): a database from the migrations alone and one with
  the sources have the same definition, owner, privileges, `SECURITY DEFINER` and configuration
  for every function and trigger whose source is as extracted (a source changed later is reviewed
  as the diff of its file); a second apply is a no-op; a function or trigger without a source, and
  a source that defines nothing, fail; a database at `0115` with synthetic rows upgrades to the
  same functions, triggers, privileges and rows; a failing source, a failed migration and a
  database behind its migrations leave nothing applied.

### Generated lists

The current rule (Slice 7b, D2; Q256). Three lists inside the sources forced an edit of a large
function, or of many trigger files, for every new event type or table. They are **inventories**
and are generated by `pnpm generate` (`packages/db/src/scripts/generate-sources.ts`, logic in
`src/generated-sources.ts`); `pnpm verify` fails when a committed generated source differs from
the generator's output.

| Generated source | The list | From |
|---|---|---|
| `functions/audit/record_audit_event.sql` | the event types the function refuses (`event_type_reserved`) | `reservedEventTypes`, the domain's audit model (`packages/domain/src/audit/events.ts`) |
| `functions/retention/retention_erase_participation.sql` | `v_tables`: the tables the erasure walks, in its order | `erasureParticipationTables` in the data catalog, without `audit_event` |
| `triggers/generated/evidence_set_phase.sql` | the evidence-only trigger `<table>_evidence_set_phase`, one identical statement per table | `participation` and `erasureParticipationTables`, without `evidenceOnlyExemptTables` |

- **A generated function is its hand-written template with the list filled in.**
  `packages/db/sql/templates/<name>.sql` is the function, with one placeholder line
  (`/*generated:…*/`) where the list stands. The function is changed in its template, the list in
  the model, and `pnpm generate` writes the source; the template is not a source and is never
  applied. A generated source starts with a header naming the generator and what it was generated
  from, and is listed in the manifest like any other source.
- **No function was added for a list**: the lists stay inside the functions that use them, so the
  set of functions and their grants are unchanged.
- **Only inventories are generated; every rule stays stated by hand.**
  - *The erasure order* is the order of `erasureParticipationTables` in
    `packages/db/src/data-catalog.ts`: a table stands before every table it references, except
    across an edge in `erasureDeferredForeignKeys`. A new table is placed there by hand;
    `data-catalog.test.ts` fails until the table is in the inventory and its place respects the
    foreign keys. `audit_event` stands last and is not deleted.
  - *The tables that stay writable in the evidence-only phase* are `evidenceOnlyExemptTables`
    (`audit_event`, `legal_hold`), stated by hand in the data catalog.
  - *Hand-written and not generated*: each retention class's deletion and its guards
    (`retention_delete_class`, `retention_classes_left`, `retention_purge_credentials`), what a
    legal hold keeps (the kinds accepted by `place_legal_hold`, the held-class roots and the
    retained FK parents inside the erasure's template), the deferred foreign keys, and the
    catalog's `retainedDependencies` and `erasureRetainedDependencies` with their release
    conditions. A new table still fails the schema tests until its retention class, its place in
    the erasure order and its dependencies are stated.
- **Adding an audit event type**: the enum value in a migration and the type in the domain's
  model (reserved or not), then `pnpm generate`. **Adding a participant table**: the table and
  its catalog entry, its place in `erasureParticipationTables`, its dependencies and, where its
  class deletes it, the hand-written deletion; then `pnpm generate`. Neither edits a function
  for its list.
- **Tested** (`generated-lists.test.ts`): the lists in the sources equal the model's; a new event
  type or table in a fixture changes only generated sources; a stale source, a name that is not
  an identifier and a template without its placeholder are refused. At the switch the generated
  lists equalled the hand-written ones (types and order), every trigger definition was identical
  and the two functions differed from the migrations' in the white space of their list only.
